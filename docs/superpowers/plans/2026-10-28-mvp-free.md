# MVP Free — implementation plan

> Execute in dependency order using superpowers:executing-plans and test-driven development. Device-dependent checks require physical evidence; never mark them complete from a build alone.

**Goal:** Deliver a local-first Android sensor and Windows theme controller meeting issue #1.
**Architecture:** Android hosts authenticated WSS and reports physical sensor state; Windows verifies identity, evaluates readings, and controls both theme values. User intent persists independently of transport health.
**Tech stack:** Flutter/Kotlin Android; .NET/Avalonia Windows; local storage and open-source dependencies.
**Spec:** `docs/superpowers/specs/2026-10-22-ambient-theme-controller-design.md`; ADRs 001–021; issue #1.

## Constraints and evidence

- No account, cloud, root, administrator, corporate-network bypass, secrets in discovery/logs, or proprietary Free dependencies.
- Simulated WebSocket over Windows hotspot is the only validated positive end-to-end transport PoC. It does not validate physical sensing, TLS, discovery, background, or themes.
- A heartbeat is not a physical sensor event; no reliable measurement means preserve theme.
- Manual pause and detectable external theme changes persist until explicit resume. Both Windows theme values are changed together; partial failure suspends automation.
- Candidate lux thresholds and timing are uncalibrated; Android background behavior and device support must be measured.

## Delivery decomposition and gates

1. **Windows theme PoC:** isolate registry read/write and external change detection; tests with an in-memory store for no-op, partial writes, own-change correlation, and external changes. Run a separate opt-in real Windows test and document visual refresh and accessibility behavior. Never change the user's theme automatically during tests.
2. **Android sensor PoC:** Flutter/Kotlin app with TYPE_LIGHT availability, accuracy, actual sensor-event timestamps, event counts and lifecycle diagnostics. Verify on two devices in foreground, minimized, locked, Doze and battery saver. Capture device/API and observed failures; do not claim background support without evidence.
3. **Android WSS/background PoC:** authenticated local server and explicit foreground session, validated certificate identity, reconnection and permission behavior on devices. Test revocation, expired invitation, TLS mismatch and service termination before adopting the design.
4. **Discovery PoC:** Android NSD plus Windows discovery and manual endpoint fallback. Measure ordinary Wi-Fi and Windows hotspot; no assumption that QR creates a route.
5. **Contracts and persistence:** versioned HELLO, LIGHT_READING, SENSOR_STATUS, ACK and errors with size, sequence, identity and freshness checks. Store versioned settings and credentials using platform-protected storage; test corrupt data, restarts and heartbeat without sensor events.
6. **Windows decision core:** deterministic hysteresis, stability and cooldown; reject invalid lux; tests at thresholds, intermediate zone, time discontinuities and recovery. User intent remains independent of connection state; failure, manual pause, external changes and partial theme updates prevent writes.
7. **Android integration:** integrate physical source, pairing approval/revocation, WSS, network changes and session UI. Verify reconnection and absence of secret material in logs and mDNS.
8. **Windows integration:** endpoint selection, verified WSS, retry/backoff, separate network/sensor watchdogs, tray and settings/onboarding UI. Test identity mismatch, changing IP, missing routes, pause during reconnect and restart.
9. **Release gate:** focused unit/integration tests and public CI; real E2E with two Android models and Windows 11; reproduce Free builds, audit licenses/NOTICE and document manual endpoint, limitations, export/import and signing/store constraints. Premium and relay remain out of scope.

## Review focus

- Unchanged on-change sensor: heartbeat cannot make stale events look fresh.
- Partial Windows update: stop automation and expose mismatch; never claim atomicity.
- External change during own writes: do not suppress a conflicting value as an own event.
- Reconnect during persisted pause: never resume until explicit user action.
- New certificate or IP: authenticate identity independently from address and reject mismatched TLS.

## Task 1: Windows theme proof of concept

**Files:** `poc/windows-theme/ThemeProbe.csproj`, `poc/windows-theme/Program.cs`, `poc/windows-theme/ThemeStore.cs`, `poc/windows-theme/README.md`, and `poc/windows-theme/tests/ThemeProbe.Tests.csproj`, `poc/windows-theme/tests/ThemeStoreTests.cs`.

**Interfaces:** `IThemeRegistry.Read(name)` and `Write(name, value)`; `ThemeController.Read()` returns both values; `Apply(light)` returns success only when both read back as requested. Registry implementation targets current-user Personalize only. Probe defaults to read-only; explicit command is required for writes.

- [ ] Add tests for matching values causing no writes, both values being applied, and a failure/readback mismatch being reported without a success claim.
- [ ] Run focused tests and confirm failure before implementation.
- [ ] Implement the interface, controller and read-only-by-default probe.
- [ ] Run focused tests and build. Document a user-controlled procedure for visual refresh and external-change experiments; no physical behavior is claimed until observed.

Subsequent tasks require separate detailed plans as PoCs resolve platform and security unknowns. They remain open and must not be represented as complete by this first task.
